PhoneBoost Android durable worker evidence
Date: 2026-09-20 (Europe/Paris)
Device: Samsung Galaxy A15 SM-A155F / RZ8X500LL3A
Android: release 16, API 36, arm64-v8a
Product transport: direct LAN; ADB forward/reverse tunnels absent

AUDIT
- MainActivity owns preferences and user actions, but does not own or stop the runtime on pause/destroy.
- PhoneBoostService owns WorkerNative, the secure runtime, ResourceGuard sampling, the TCP listener, and DNS-SD.
- Manifest FGS type is connectedDevice with FOREGROUND_SERVICE_CONNECTED_DEVICE and CHANGE_NETWORK_STATE.
- compileSdk/targetSdk/minSdk: 37/37/29. AGP 9.3.0, Gradle 9.5.0, Java 17.
- Pairing state and the ON preference are persisted. Worker incarnation, lease, sessions, and listener are process-local.
- No product path uses ADB, USB debugging, WorkManager, AlarmManager, CompanionDeviceManager,
  CompanionDeviceService, BOOT_COMPLETED, FLAG_KEEP_SCREEN_ON, or a wake lock.
- The product transport is IP. Wi-Fi is preferred for the diagnostic address; another site-local IPv4
  interface, including USB Ethernet when provided by Android, can be selected. A raw USB cable is not a
  PhoneBoost transport.

PLATFORM DECISION
- A user-started connectedDevice foreground service is the narrow supported mechanism for this continuous,
  user-visible external-device interaction.
- Companion Device Manager was not selected: it performs a user-approved Bluetooth/BLE/Wi-Fi companion
  association but does not create the connection, and PhoneBoost already has its own authenticated LAN peer.
- WorkManager was not selected: a long-running worker still uses an FGS and does not improve the live listener.
- No battery-optimization exemption or permanent/bounded wake lock was added. The screen-off job completed
  without one.
- Android Doze can suspend network access. The physical proof below used USB power and proves screen-off/
  keyguard behavior, not forced deep Doze.
- Android Service.START_STICKY is appropriate for a user-enabled service intended to run for an arbitrary
  period. Android user stop/force-stop remains authoritative and is not bypassed.

ROOT CAUSE
- Previous screen wake requirement: MAESTRO_ONLY + KEYGUARD_AUTOMATION_LIMITATION for UI/SAS actions.
- It was not an Activity lifecycle, socket background, ADB transport, or screen-off runtime failure.
- Separate durability gap found: SERVICE_LIFECYCLE_BUG. START_NOT_STICKY instructed Android not to recreate
  the service after process reclamation. The service now returns START_STICKY and reloads persisted trust.

LIMITS
- Forced deep Doze while unplugged: NOT RUN; Android documents that Doze suspends network access.
- Reboot auto-start: NOT IMPLEMENTED / NOT CLAIMED. ON preference and pairing persist, but the user must open
  PhoneBoost after reboot. No BOOT_COMPLETED FGS start was added.
- Raw USB without an IP interface: unsupported as a product transport.
